## OrderBook 功能介绍

orderBook 能够直观的展示整个交易市场买卖盘的挂单情况，
通常用户高卖低买的单子不能立即成交，会变成委托单展示在盘口，盘口即表明目前市场上待成交买卖单的情况，
用户市价单或者 卖价低于买一价 买价高于卖一价，都会以最优价成交，买单的话即从卖一价的挂单开始成交，
根据用户设定的交易模式可能会以卖二价成交，即滑点。


####  orderBook 前端显示

上面为操作区，拖拽的区域，买卖盘切换按钮，合并深度切换下拉。
主盘口区域：从上到下 为 卖盘，lastPrice / indexPrice / markPrice ，买盘， 买卖占比。
lastPrice 代表市场每成交一次的最新价格，同时 会和上一次的价格做对比来判断涨跌。
买卖盘一般都会展示每一个价格对应的 挂单量，以及他前面所有待成交挂单量和自己挂单量累加值，还有基于最大值百分比
最大值的取法：单独买盘：买盘最大值 单独卖盘：卖盘最大值 买卖盘： 买卖盘的最大值。
所以买卖盘都在情况下可能会出现其中一个方向的盘达不到100%的情况。


#### orderBook 前端交互

买卖盘切换展示：单独买盘 单独卖盘 买卖盘
用户切换合并深度，eg：0.01 0.1 1 10 10 不同交易对根据精度会有所不同。
合并深度的原则，eg: 0.01->0.1 的切换， 0.15 在 卖盘 向上合并 即 0.2 在买盘 向下合并 即 0.1
用户拖拽：左右拖拽 宽度变化，上下拖拽，会根据 盘口高度动态计算 买卖盘 需要显示多少档。


#### 数据模型
典型的 L2 订单簿（Market-by-Price，按价格聚合）结构如下
每次推送相同的价格数量替换，数量为0，直接移除。

[orderbook.ts](./orderbook.ts)

```ts

interface OrderBook {
    bids:  Arrary<OrderLevel>,  // 买单：价格从高到低
    asks:  Arrary<OrderLevel>,  // 卖单：价格从低到高
    last_seq: Number,                         // 当前序列号，用于检测丢包
}

interface OrderLevel {
    price: Number,       // 价格（生产环境建议用整数表示）
    volume: Number,     // 委托量
    sumVolume: Number,        // 累加委托量
    sumVolumePercent: Number,        // 累加委托量百分比
```

#### 数据补偿机制

- 前端来做
    序列号校验：每条增量消息都带有一个单调递增的序列号（Sequence Number）。客户端每应用一条消息，都会记录当前的序列号 lastSeq。收到新消息时，会校验其序列号 seq 是否等于 lastSeq + 1。
    触发补偿：如果 seq > lastSeq + 1，说明中间有数据丢失，本地订单簿已“中毒”，需要立即触发补偿流程。
    补偿流程：立马请求快照，在快照返回期间推送数据保存在 队列里，快照返回后，拿快照 seq+1去取缓存的 推送 重新 update
    [orderbook数据补偿.ts](./orderbook数据补偿.ts)

- 后端来做
  后端每次发现有跳号就推一次全量数据，
  ws 每次连接先推全量数据

#### 合并深度

可以选择 0.01 0.1 1 10 合并，
卖盘价格区间内向上合并
买盘价格区间内向下合并
先按照前端的数据去合并，这时候会出现盘口数据不满的情况。
同时立马按照发起新的深度订阅ws, 取消老的深度订阅ws
返回的数据进行填充。

#### 性能优化

orderBook 数据需要经过 频繁的数据计算并触发更新，大量长任务会占据 主线程。同时频繁的更新也会拖累浏览器的FPS
所以将 累加排序和百分比计算 下沉至 web worker 里面计算 将计算好的数据 按照 300ms 降频 发送至 主线程 显示。

大行情下，增加缓存对列，缓存数据， 同时将 300ms 内的数据进行排序和 按照price 去重取最新的挂单量。
时间上 降频至 300ms 降频处理。同时缓存对列，会限制数据总量和去除active 时间外的数据。
